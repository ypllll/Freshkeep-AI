# FreshKeep AI

帮助用户数字化管理家中冰箱里的食材，并基于**真实库存**规划菜谱，减少遗忘食材与不必要的浪费。

> 本文件只描述**当前仓库里已经存在**的能力。未实现的阶段在「尚未实现」一节单独列出。

## 当前状态

**阶段 3：日期与过敏原 —— 已完成，等待审核。**

阶段 0（文档基线）、阶段 1（骨架与持久化底座）、阶段 2（数字冰箱核心）、阶段 3（日期与过敏原）均已完成；阶段 4 ~ 6 尚未开始。

已经可以实际使用的能力：

- 录入食材批次、查看汇总与批次明细；
- 修改批次数量、消耗、丢弃；
- 未指定批次时按固定顺序自动分配扣减；
- 所有库存数量变化都有事件记录，一次操作整体事务化；
- 保质期：用户填写的有效期原样保存，只填天数不生成正式日期，没有明确期限时给出标注清楚的「AI 估算」；
- 过敏原：维护个人过敏原清单，逐批次判定冲突 / 待核实 / 未发现已知冲突。

尚未实现：真实 AI 调用、食谱规划、确认菜谱消耗。目前**没有接入任何大模型**：日期里的「AI 估算」是本地经验规则算出来的、只用于展示，`pages/2_食谱规划.py` 仍是占位页面。

## 快速开始

环境要求：Python 3.11+（本仓库在 Python 3.13.14 上验证通过）。

```bash
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
streamlit run app.py
```

启动后：首页 `app.py` 只展示项目进度与只读运行参数；点击侧边栏进入 **数字冰箱** 页面即可实际录入与操作数据。占位页面（食谱规划）还没有功能。

> 注意：首页 `app.py` 里的进度文案尚未同步到阶段 2，仍写着阶段 1 的说明。该文件不在本阶段的允许修改范围内，待后续授权后再更新。

### 配置

- 唯一会被读取的环境变量是 **`DATABASE_PATH`**（SQLite 文件路径，默认 `data/freshkeep.db`，相对于项目根目录）。
- 目前**不会自动加载 `.env` 文件**：`.env.example` 只是模板，自动加载要等阶段 4 引入 `python-dotenv` 之后才生效。现阶段请直接设置 shell 环境变量，例如 `$env:DATABASE_PATH = "D:\freshkeep.db"`。
- `DUE_SOON_DAYS = 2` 是固定业务常量，不提供配置项，也无法用环境变量覆盖。
- `OPENAI_API_KEY` / `OPENAI_BASE_URL` / `OPENAI_MODEL` 等变量在阶段 4 才会用到，现在无需设置。

## 已实现的功能（阶段 2–3）

数字冰箱页面有五个标签页：**库存总览**、**入库**、**消耗 / 丢弃 / 修改**、**过敏原清单**、**事件记录**。

- **入库**：每次购买新增一条独立批次记录，同名食材不会被覆盖（`R-15`）。购买日期可留空（留空=未知，不默认今天）；有效期日期可留空，用户填写的日期原样保存（`R-25`、`R-01`）。
- **查询**：按"归一化名称 + 单位"汇总活动批次数量，可展开查看各批次的批次 ID、数量、购买日期、储存方式、保质期、期限来源、新鲜度、参考信息、AI 估算、过敏原、提示与状态。汇总值恒等于各活动批次数量之和（`R-15`）。
- **保质期**：用户填写的有效期日期直接采用；只填天数时保留天数、`expiry_date` 保持 NULL（`R-26`）；日期与天数冲突时保留两者并以日期为正式记录，提示渲染在明细的"提示"列，刷新后仍可见（`R-04`）。
- **AI 估算**：没有明确有效期但填了购买日期时，按类别 + 储存方式的经验区间给出估算日期区间，标注"AI 估算"，只展示、不落库、不参与新鲜度分级；没有购买日期时不生成（`R-30`）。
- **通用参考区间**：类别 + 储存方式的经验天数区间与依据，单列展示且带"参考信息，非食品安全保证"，不换算成日期（`R-03`）。
- **过敏原**：维护个人过敏原清单（`user_allergen`），逐批次判定 `conflict` / `unverifiable` / `none_known`；`none_known` 的文案固定为"未发现已知冲突（不代表安全）"（`R-05`~`R-08`、`R-14`）。
- **修改数量**：修改指定批次的数量并写入 `edit` 事件；数量没有变化时不写事件（`R-23`）。
- **消耗 / 丢弃**：可按食材操作（自动分配批次），也可指定单个批次（`R-16`）。超量请求被拒绝，库存不会变成负数；指定批次不足时直接拒绝，不会跨批次补足（`R-24`）。
- **自动分配顺序**（`§6.5`，固定且可复现）：① 有用户填写期限的批次优先，按期限从早到晚；② 同期限按购买日期从早到晚，购买日期未知的排在已知日期之后；③ 仍相同按批次 id 升序；④ 没有正式期限的批次一律排在已知期限之后。AI 估算不是用户期限，**不会**让批次插队。
- **分配结果可见**：界面会逐批次列出扣减前数量、扣减量、扣减后数量。
- **事件记录**：所有库存数量变化都写入 `inventory_event`，语义为 `qty_delta = 变更后数量 − 变更前数量`：入库为正，消耗与丢弃为负，修改数量记录差值，变化为 0 不写事件（`R-23`）。
- **事务性**：一次操作涉及的多次扣减、对应事件写入与状态更新共用同一个数据库连接与事务，任一步失败整体回滚（`R-22`）。
- **数据层校验**：名称、数量（有限且 > 0）、单位 / 类别 / 储存方式白名单、购买日期都在数据层校验，不依赖界面控件的限制（`R-10`、`R-24`）。
- **持久化**：数据存放在单个 SQLite 文件，重启后仍然存在。

批次状态：数量通过消耗归零时变为 `consumed`，通过丢弃归零时变为 `discarded`；只能通过消耗或丢弃清零，修改数量不接受 0 或负数。

已知限制：不做单位换算，同名不同单位分开汇总；通用参考区间与 AI 估算都是粗略经验值（来源待补）、不构成食品安全依据；AI 估算不使用用户填写的天数，只看类别与储存方式；过敏原别名表与复合调味料清单覆盖有限，未命中只表示"未发现已知冲突"。

## 数据库

- 结构由 `PRAGMA user_version` 版本化管理，当前版本为 **3**：
  - 版本 1：`inventory_item` —— 一行即一条购买批次；
  - 版本 2：`inventory_event` —— 库存数量变化的事件记录，`item_id` 指向具体批次；
  - 版本 3：`user_allergen` —— 用户过敏原清单（`display_name` / `name_normalized` UNIQUE / `created_at`）。
- 升级只追加新版本步骤，已发布的步骤不修改；重复初始化是幂等的，不会重复建表或破坏数据。
- 迁移失败会**报错停止并回滚当前步骤**，`user_version` 保持不变，不会删除、重建或清空数据库。
- 数据库文件默认在 `data/freshkeep.db`（`data/` 已被 `.gitignore` 排除），在首次打开「数字冰箱」页面时自动创建。

## 核心安全规则摘要

完整表述与验收方式见 [docs/product_spec.md](docs/product_spec.md) 第 6 节。

| 规则 | 摘要 |
|---|---|
| R-01 | 用户提供的信息优先于系统估算 |
| R-02 | 未知保质期不得被伪装成确定的安全期限；AI 估算必须标注为估算，不得冒充用户提供的有效期 |
| R-03 | 保质期参考区间不得伪装成确定到期日期或食品安全保证；展示时必须同时标注"参考信息，非食品安全保证" |
| R-04 | 用户日期与用户天数冲突时，以具体日期为准并提示信息冲突 |
| R-05 ~ R-06 | 过敏原是硬约束，由 Python 判定，结果为三态 |
| R-07 | 成分无法核实的菜谱不得作为普通推荐，进入独立的"待核实区域" |
| R-08 | "未发现已知冲突"不得表述为"安全" |
| R-09 | 菜谱规划不修改库存，只有用户确认实际消耗后才更新 |
| R-10 | 库存计算、输入校验与关键业务约束由 Python 负责 |
| R-11 | 食谱规划必须使用实际库存数据 |
| R-12 | 库存变更必须事务化并可审计 |
| R-13 | AI 输出必须经过结构校验，不通过即拒绝 |
| R-14 | 不确定的食材成分必须明确标记 |
| R-15 | 每次购买新增独立批次记录，不得覆盖旧记录 |
| R-16 | 消耗需指定批次，或按明确、可解释、可测试的规则分配 |
| R-17 | 规划不改库存；用户选定菜谱后按最新库存重新计算 |
| R-18 | 食材不足属正常情况，展示现有量/需求量/缺少量；调整份数时所有食材同步按比例换算 |
| R-19 | 未匹配食材表示"库存未知"（NULL），不得当作 0；已知无剩余（曾匹配到记录、批次已全部耗尽）按 0 处理并正常计算缺口与补购；未经确认的未知量不计入缺失与补购 |
| R-20 | 候选菜谱可能互相替代，缺少量不得相加；只计算用户选中的菜谱 |
| R-21 | 整份响应不符合 Schema 则拒绝整份；单道菜谱业务错误只丢弃该菜谱 |
| R-22 | 库存检查、更新、事件写入与状态更新在同一事务内完成；已应用的规划不可重复应用 |
| R-23 | `qty_delta = 变更后 − 变更前`（新增为正、消耗与丢弃为负、编辑记差值） |
| R-24 | 超量消耗/丢弃必须拒绝，库存不得为负；数量不明确时向用户追问 |
| R-25 | 购买日期由用户主动填写、允许留空（留空=未知，不得默认今天）；如使用"今天"必须由用户确认并留痕 |
| R-26 | 只提供天数时：保留天数、不生成正式有效期日期、分级为"未知"；购买日期未知时不生成 AI 估算日期 |
| R-27 | 份数缩放按同一比例换算全部食材，保留 2 位小数；计件单位另给整数准备建议，不改写记录值 |
| R-28 | 菜谱需求量与实际消耗量是两个量；可只确认部分食材，未确认的不做任何变动 |
| R-29 | 跨多批次扣减时逐批次计算、逐批次更新并逐条写事件，全部在同一事务内 |
| R-30 | AI 估算只用于展示：由类别 + 储存方式的经验区间配合购买日期算出，绝不写入 `expiry_date`、不参与新鲜度分级，必须标注"AI 估算" |

## V1 范围

数字冰箱（新增 / 查看 / 修改 / 消耗 / 丢弃 + 按批次记录每次购买 + 本地持久化）；保质期记录与参考区间（购买日期可标记未知）；过敏原硬约束与待核实区域；基于真实库存的食谱规划（候选菜谱、推荐理由、现有量/需求量/缺少量/补购建议）；确认后在同一事务内更新库存并写入事件。

库存闭环：首次初始化 → 购买入库 → 查询与规划 → 用户选择菜谱 → 确认实际消耗 → 更新库存与事件。取出食材不改变库存，只有确认消耗或丢弃才减少数量。

## V1 明确不做（冻结）

多智能体架构、RAG / 向量数据库、用户账号与云同步、图像识别、外部购物平台集成、复杂优化算法、多模型 Provider 插件系统、跨维度单位换算、营养与成本分析、提醒推送、移动端适配、多语言、对话式（自然语言）库存记账入口。

对话式入口虽不在 V1 实现，但其不变量在 V1 已生效：任何入口写入的数量都必须经 Python 校验并由用户确认，AI 不得直接决定数据库中的最终数量。**V1 的库存操作只通过表单进行。**
