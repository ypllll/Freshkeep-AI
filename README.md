# FreshKeep AI

FreshKeep AI 是一个**本地运行**的家庭食材管理与菜谱规划应用：把冰箱里的食材按采购批次记录下来，
根据真实库存调用大模型生成菜谱候选，再由程序算出还缺什么、是否有过敏原风险，
并在你确认实际用量后按批次扣减库存、留下消费记录。

## 它解决什么问题

- **食材被遗忘**：只记得"买过"，不记得数量、购买日期和有效期，最后只能扔掉。
- **菜谱和库存脱节**：网上找的菜谱不会告诉你家里的番茄还剩几个、够不够做。
- **过敏原靠记忆**：家里有人对花生、牛奶过敏时，需要一层不依赖"感觉"的检查。
- **计划与消耗混为一谈**：看过一份菜谱不等于真的用掉了那些食材，用量需要由你确认。

适合的场景：个人或家庭在一台电脑上管理自己的冰箱，数据保存在本机 SQLite 文件里，
不涉及账号、云同步或共享库存。

## 核心功能

| 功能 | 说明 |
|---|---|
| **库存与独立采购批次** | 每次入库新增一条独立批次记录，同名食材不会被覆盖；界面按"名称 + 单位"汇总展示，同时可展开查看每个批次的购买日期、储存方式与状态 |
| **消耗 / 丢弃 / 修改数量** | 可以指定某一个批次，也可以只给出数量：程序按固定顺序（先到期先消耗，期限未知的排最后）跨批次分配，并逐批次展示实际扣减量 |
| **日期与参考保质期** | 你填写的有效期日期**原样保存**，系统不会覆盖或重算；只填天数时保留天数、正式期限保持"未知"；没有明确期限时给出标注清楚的「AI 估算」（由本地经验区间计算，**不调用任何模型**） |
| **已知过敏原约束** | 维护个人过敏原清单，逐批次判定三态：`已确认冲突` / `待核实` / `未发现已知冲突`；内置有限的别名与常见复合调味料清单，判定由程序完成，不依靠提示词 |
| **AI 菜谱生成** | 根据你的需求和当前库存（含数量、单位、过敏原声明）调用 OpenAI 兼容接口生成候选菜谱；输出必须通过严格的 JSON 契约校验，不合格就整份拒绝 |
| **食材缺口计算** | 需求量来自模型，**现有量与缺口由程序计算**：同名同单位跨批次汇总；单位不一致标记"单位无法比较"（不做换算）；库存里没有记录的食材按"未知"处理，不当成 0 |
| **确认后扣减库存** | 生成菜谱**不会**改动库存；只有在确认环节勾选并填写实际用量后，才会重新读取最新库存、通过过敏原闸门，再按批次扣减 |
| **变更与消费事件** | 所有数量变化都会留痕，语义为 `qty_delta = 变更后数量 − 变更前数量`；菜谱扣减额外记录 `source=recipe_plan` 与本次规划编号，一次确认产生的多条批次事件在同一事务中写入 |

## 技术栈与架构

**技术栈**：Python 3.11+、Streamlit（界面）、SQLite（标准库 `sqlite3`，本地持久化）、
OpenAI 兼容 API（`openai` SDK，通过 `base_url` 指向任意兼容端点）、pydantic（模型输出校验）、pytest（测试）。

**分层**（依赖方向单向，`UI → Services → {Core, Storage, AI}`）：

| 层 | 目录 | 职责 |
|---|---|---|
| UI | `app.py`、`pages/` | 只做输入与展示：表单、列表、提示。不做计算、不写 SQL、不直接创建 SDK 客户端 |
| Services | `services/` | 业务流程编排与事务边界：库存操作、AI 调用入口、菜谱规划与确认扣减 |
| Core | `core/` | 纯业务规则：输入校验、批次分配、保质期与参考区间、过敏原判定、缺口计算。不依赖数据库与网络 |
| Storage | `storage/` | SQLite 持久化：连接与显式事务、版本化迁移、各实体的 SQL |
| AI | `ai/` | 模型接入与输出契约：提示词、OpenAI 兼容客户端、pydantic 校验。唯一的网络出口 |
| 配置 | `config.py` | 运行参数（数据库路径、AI 配置）与固定业务常量 |

**数据与一致性**：

- 数据存放在单个 SQLite 文件（默认 `data/freshkeep.db`，已被 `.gitignore` 排除），首次打开「数字冰箱」页面时自动创建；
- 表结构由 `PRAGMA user_version` 版本化迁移管理，当前版本为 **3**（`inventory_item` / `inventory_event` / `user_allergen`）；
  迁移只追加新版本步骤，失败时报错停止并回滚，不会删除或重建数据库；
- 涉及数量变更的操作使用条件更新（`WHERE … AND quantity >= ?`）并校验受影响行数，配合显式事务保证"要么全部成功、要么全部回滚"。

## 安装与运行

### 1. 准备环境

要求 Python 3.11 或更高版本（本项目在 Python 3.13 上开发与验证）。

```bash
python -m venv .venv
```

激活虚拟环境（任选与你的终端匹配的一条）：

```bash
# Windows（cmd）
.venv\Scripts\activate.bat
# Windows（PowerShell）——若提示"禁止运行脚本"，请改用上面的 activate.bat，或直接用 .venv\Scripts\python.exe 执行命令
.venv\Scripts\Activate.ps1
# macOS / Linux
source .venv/bin/activate
```

### 2. 安装依赖

```bash
pip install -r requirements.txt
```

### 3. 配置 AI 模型

AI 配置从环境变量读取，也可以写在项目根目录的 `.env` 里（由 `python-dotenv` 按需加载，`.env` 已被 `.gitignore` 排除）：

```bash
cp .env.example .env      # Windows: copy .env.example .env
```

```ini
OPENAI_API_KEY=your_api_key
OPENAI_BASE_URL=https://your-compatible-api-endpoint.example/v1
OPENAI_MODEL=your-model-name
AI_TIMEOUT_SECONDS=30
```

| 变量 | 作用 | 缺省行为 |
|---|---|---|
| `DATABASE_PATH` | SQLite 文件路径 | 默认 `data/freshkeep.db`（相对项目根目录） |
| `OPENAI_API_KEY` | 模型 API Key | 留空也能启动应用；只有真正调用模型时才提示缺少配置 |
| `OPENAI_BASE_URL` | OpenAI 兼容服务地址 | 留空时使用 SDK 默认地址 |
| `OPENAI_MODEL` | 模型名称 | 留空时调用会报"缺少 `OPENAI_MODEL`" |
| `AI_TIMEOUT_SECONDS` | 单次请求超时秒数 | 默认 30；写成非法值也会回退到 30，不会崩溃 |

> `DUE_SOON_DAYS = 2`（临期阈值）是代码里的固定业务常量，不提供配置项，也无法用环境变量覆盖。

想看模型是否真的连得通（会发起一次真实请求，只打印配置摘要和模型回复，不打印 Key）：

```bash
python scripts/check_ai_connection.py
```

### 4. 启动应用

```bash
streamlit run app.py
```

默认地址为 <http://localhost:8501>（端口被占用时可用 `--server.port 8502` 指定其他端口）。

### 5. 运行测试

```bash
python -m pytest --basetemp=.pytest_tmp
```

## 基本使用流程

1. **管理库存**（侧边栏 →「数字冰箱」）
   - 「入库」标签：填写名称、类别、数量、单位、储存方式；购买日期与有效期都可以留空（留空 = 未知，系统不会默认成今天）；
   - 「库存总览」：查看按名称汇总的总量与各批次明细；
   - 「消耗 / 丢弃 / 修改」：可以按食材自动分配批次，也可以指定单个批次；
   - 「过敏原清单」：维护你自己的过敏原（例如花生、牛奶），判定时才有个性化依据；
   - 「事件记录」：查看所有数量变化。
2. **生成食谱**（侧边栏 →「食谱规划」）
   - 填写需求（例如"想吃清淡的家常菜"）与计划份数，点「生成菜谱候选」；
   - 系统把当前库存汇总与你的过敏原清单一起发给模型，再由程序校验结构、判定过敏原、计算缺口。
3. **查看缺口与过敏原状态**
   - 每道菜列出：计划用量、最新可用、还缺多少、是否可扣减；
   - `已确认冲突` 的菜谱不会出现在推荐里；`待核实`（成分无法核实）的菜谱单独列出，不作为普通推荐。
4. **确认食材消耗**
   - 在「确认实际消耗」区域选择菜谱，勾选真正用掉的食材并填写实际数量，点「确认并扣减库存」；
   - 成功后显示每种食材实际扣减量、涉及的批次、扣减后剩余，以及本次写入的消费事件条数。

## 重要说明与限制

- **日期与参考期不是食品安全保证**：界面上的「参考信息」是内置的粗略经验区间（来源待补），「AI 估算」是按类别与储存方式推算的参考值；两者都不会写成正式有效期，也不能用来判断食物是否安全。
- **"未发现已知冲突"不等于安全**：过敏原判定只依据你已声明的信息与内置的有限别名/复合调味料清单；成分未声明、或菜谱用了库存里没有的食材，都会被标为"待核实"而不是"无冲突"。
- **规划与扣减是两个环节**：生成菜谱只读取库存，不写任何数据；只有你在确认环节明确勾选数量后才会扣减。
- **名称匹配是保守的**：只做归一化后的精确匹配，不做模糊或同义词匹配（例如库存写"番茄"、菜谱写"西红柿"会被判为未匹配）；单位不做换算（`L` 与 `ml` 视为无法比较）。
- **防重复应用只在当前会话内有效**：同一份规划在当前会话里不能重复确认扣减，但**没有**持久化规划表，应用重启或换一个会话后，同一份规划可以被再次确认——这不是数据库级的幂等保障。
- **菜谱不落库**：每次生成的规划只存在于本次会话中，刷新会话后需要重新生成；也没有份数重规划（只按生成时指定的份数展示用量）。
- **单用户、本地运行**：没有账号、权限、云同步与多用户共享，也不提供移动端适配。

## 测试

```bash
python -m pytest --basetemp=.pytest_tmp
```

当前测试集共 **433** 项，全部通过（失败 0）。覆盖内容包括：数据库连接与版本化迁移（含失败回滚与数据保留）、
输入校验与名称归一化、批次分配与汇总一致性、保质期与参考区间、过敏原三态判定、AI 客户端与输出契约、
菜谱缺口计算、确认扣减的事务回滚与逐批次事件，以及用 Streamlit `AppTest` 驱动的界面层测试。

两点说明：

- 测试全程使用一次性临时数据库与假模型客户端，**不会访问真实 API、不写入你的数据**；
- `--basetemp=.pytest_tmp` 把 pytest 临时目录放在项目内（已被 `.gitignore` 排除）。若某台机器的系统临时目录不可访问，
  必须带上这个参数；也请不要并行运行多个 pytest 实例，它们会共用同一个临时目录。

## 后续方向

- **份数重规划**：改份数后按同一比例重算全部食材用量，并重新校验缺口与可扣减数量；
- **菜谱持久化与历史**：把规划与确认结果落库，为跨会话的防重复与历史回溯提供依据；
- **匹配能力**：在保守精确匹配之外，补充可解释的别名/同义词表（而不是模糊匹配）；
- **参考数据来源**：为内置的参考保质期区间补充可核查的来源，或改为可维护的数据文件；
- **更正路径**：为确认后的扣减提供显式的撤销/更正操作（当前只能回到数字冰箱手动改回数量）。
