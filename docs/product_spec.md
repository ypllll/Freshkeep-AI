# FreshKeep AI —— 产品规格（V1）

## 1. 文档目的与适用范围

本文档定义 FreshKeep AI V1 的产品范围、业务规则、用户流程与验收口径。所有规则使用稳定编号 `R-xx`，架构文档与测试计划引用同一编号，以保证"规格 / 设计 / 测试"三处口径一致。

本文档不描述代码结构；实现约束见 [architecture.md](architecture.md)。

## 2. 产品定位

帮助用户数字化管理家中冰箱里的食材，并依据**真实库存**规划菜谱，减少遗忘食材与不必要的浪费。两个核心模块同等重要：**数字冰箱**与**智能食谱规划**。

单用户、本地运行、面向个人日常使用；不涉及账号体系与云端数据。

## 3. V1 范围

| 模块 | V1 内容 |
|---|---|
| 数字冰箱 | 新增、查看、编辑、消耗、丢弃食材；**按批次记录每次购买**，按名称汇总展示总量并可展开查看各批次明细；按状态与新鲜度筛选；本地持久化，进程重启后数据不丢失 |
| 保质期 | 原样保存用户填写的有效期日期；支持只填天数（保留天数、不生成正式日期）；购买日期允许留空；有购买日期时可给出标注清楚的 **AI 估算**；信息不足时明确显示未知 |
| 过敏原 | 用户维护过敏原清单；食材标记过敏原声明状态；规划结果按三态处理，待核实菜谱分流到独立区域 |
| 食谱规划 | 基于真实库存生成候选菜谱并展示推荐理由；用户选定菜谱后按**最新库存**重算现有量、需求量、缺少量与补购建议；食材不足属正常情况 |
| 确认消耗 | 用户确认实际用量后，在同一事务内更新库存、写入事件并更新规划状态 |

## 4. V1 非目标（冻结）

多智能体架构；RAG / 向量数据库 / 嵌入检索；用户账号、登录、云同步与多设备；图像识别与拍照录入；外部购物平台或电商集成；复杂优化算法（线性规划、多目标优化等）；多模型 Provider 插件系统；条码扫描；提醒推送；移动端适配；多语言 / 国际化；营养与热量分析；成本核算；跨维度单位换算（如 g ↔ 个）；多用户共享库存；导出 PDF / Excel 与 CSV；食谱收藏夹管理界面；**对话式（自然语言）库存记账入口**。

关于最后一项：产品层面要求"任何入口写入的数量都必须经 Python 校验并由用户确认"（R-10、R-22），该不变量对 V1 的表单入口同样成立；对话式入口本身列入 V2（见第 12 节），不在 V1 实现。

上述需求如需实现，统一记入第 12 节 V2 候选，不在 V1 内讨论。

## 5. 术语表

| 术语 | 含义 |
|---|---|
| 库存项 | 一条食材记录，含名称、类别、数量、单位、购买日期、储存方式、保质期信息、过敏原状态 |
| 批次 | 一次购买的独立记录。同一名称的多次购买会产生多条批次记录，各自保存数量、购买日期、保质期信息与状态 |
| 汇总库存 | 同名（归一化后）且同单位的批次数量合计，仅用于展示与查询；权威数据始终是各批次记录 |
| 消耗分配 | 用户未指定批次时，由系统依据明确、可解释的规则决定消耗哪些批次；结果必须可复现、可测试 |
| 用户日期 | 用户直接输入的保质期或最佳食用日期 |
| 用户天数 | 用户输入的保质天数 |
| 参考区间 | 系统依据食材类别与储存方式给出的**通用天数量程**，仅作参考；与针对单个批次的 AI 估算不同 |
| AI 估算 | 针对**某一条批次**、由类别 + 储存方式的经验区间与购买日期算出的估算日期区间；只展示，不落库 |
| 新鲜度分级 | 过期 / 临期 / 新鲜 / 未知 |
| 硬约束 | 由 Python 代码判定、不依赖 AI 的规则 |
| 待核实区域 | 成分无法确认因而不能作为普通推荐的菜谱的独立展示区域 |
| 未匹配食材 | AI 提出的食材无法对应到任何库存记录。表示"库存情况未知"，不表示"数量为 0" |
| 菜谱需求量 | 按目标份数换算后，这道菜理论上需要的食材数量。不等于实际用掉的数量 |
| 实际消耗量 | 用户确认真正用掉的食材数量。可以只覆盖部分食材，且不受菜谱需求量约束（但不得超过可用库存） |

## 6. 关键业务规则

### 6.1 规则清单

| 编号 | 规则 |
|---|---|
| R-01 | 用户提供的日期信息优先于系统估算 |
| R-02 | 未知保质期不得被伪装成确定的安全期限；AI 估算必须标注为估算，不得冒充用户提供的有效期 |
| R-03 | 保质期参考区间不得伪装成确定的到期日期或食品安全保证；参考表只收录有限组合，未收录即未知；通用参考区间与针对该批次的 AI 估算必须分列展示 |
| R-04 | 用户提供的具体日期与用户提供的天数发生冲突时，以**具体日期**作为优先记录，同时向用户提示信息冲突 |
| R-05 | 过敏原属于硬约束，不能只依赖提示词过滤，判定由 Python 代码完成 |
| R-06 | 过敏原判定为三态：`conflict`（已确认冲突）/ `unverifiable`（无法核实）/ `none_known`（未发现已知冲突） |
| R-07 | 当用户声明了相关过敏原，而菜谱中某些成分无法核实时，该菜谱不得被当作符合过敏要求的普通推荐，必须进入独立的**待核实区域** |
| R-08 | `none_known` 只能表述为"未发现已知冲突"，不得表述为"安全""无过敏原""适合过敏人群" |
| R-09 | 食谱规划不得直接修改库存；只有用户确认实际消耗后才能更新库存 |
| R-10 | 库存数量计算、输入验证和关键业务约束由 Python 代码负责，不得完全交给 AI；AI 只能提出建议或解析用户意图，数据库中的最终数量必须由 Python 依据经用户确认的输入计算得出 |
| R-11 | 食谱规划必须使用实际库存数据，不能只根据用户的泛化描述生成菜谱 |
| R-12 | 库存变更必须在单个事务内完成，且必须留有可审计的事件记录 |
| R-13 | AI 输出必须经过结构校验；校验不通过即拒绝，不做修补、不补默认值、不猜测缺失字段 |
| R-14 | 不确定的食材成分必须明确标记，不得静默视为安全 |
| R-15 | 同一食材的不同购买批次必须分别记录：每次购买新增一条批次记录，不得用新记录覆盖旧记录 |
| R-16 | 消耗必须指定批次，或由系统依据明确、可解释且可测试的规则分配；分配规则不得凭空推断未知的到期信息 |
| R-17 | 菜谱规划阶段不得修改库存；用户选定菜谱后必须基于最新库存重新计算，不得沿用生成规划时的旧数量 |
| R-18 | 食材不足属于正常业务情况：展示现有量、需求量、缺少量并给出补购建议，不因此拒绝整道菜谱；调整目标份数时，所有相关食材按比例同步换算并由 Python 校验 |
| R-19 | 未匹配食材表示"库存情况未知"：不得视为 0、不得表述为"家里没有"、未经用户确认不得计入缺失量与补购汇总 |
| R-20 | 多个候选菜谱可能互相替代，不得把候选菜谱的缺少量相加；V1 只对用户选中的菜谱计算缺口与补购建议 |
| R-21 | AI 校验分层：整份响应无法解析或不符合严格 Schema 时拒绝整份；通过 Schema 后，单道菜谱的业务错误只丢弃该菜谱，其余合法菜谱保留 |
| R-22 | 同一业务操作的库存检查、库存更新、事件写入与规划状态更新必须在同一个 SQLite 连接与事务内完成，任一步失败整体回滚；已应用的规划不得重复应用 |
| R-23 | 事件数量语义固定为 `qty_delta = 变更后数量 − 变更前数量`：新增为正、消耗与丢弃为负、数量编辑记录差值 |
| R-24 | 消耗或丢弃数量超过可用库存时必须拒绝并提示用户核实，库存数量不得变为负数；数量不明确时应向用户追问，不得猜测 |
| R-25 | 购买日期由用户主动填写，**允许留空**；留空表示"未知"，不得默认今天；如使用"今天"必须由用户确认并记录是否采用了默认值 |
| R-26 | 用户只提供保质期天数时：保留天数、**不生成正式有效期日期**（`expiry_source=user_days_unresolved`）、新鲜度为"未知"；购买日期未知时**不生成 AI 估算日期**，也不得假定购买日期为今天 |
| R-30 | AI 估算只用于展示：基于类别与储存方式的经验区间 + 用户填写的购买日期，**绝不写入 `expiry_date`**、不参与新鲜度分级，必须标注"AI 估算"且不得宣称食品安全 |
| R-27 | 份数缩放：所有相关食材按**同一比例**换算，结果由 Python 校验；缩放值保留 2 位小数（四舍五入）；不可分割单位（个 / 瓶 / 盒 / 包 / 袋 / 把 / 份）的缩放结果若为非整数，另行给出"建议按整数准备（向上取整）"提示，但不改写记录值；不做跨维度单位换算；AI 不得自行决定取整结果 |
| R-28 | 菜谱需求量与用户确认的实际消耗量是两个不同的量：用户可以只确认部分食材的实际消耗，未确认的食材不做任何库存变动；Python 不得静默修改用户确认的数量 |
| R-29 | 一种食材分布在多个批次时，由 Python 按 R-16 的分配规则计算每个批次的扣减量；每个批次的扣减各自更新库存、各自写入事件；全部扣减、事件写入与规划状态更新在同一事务内完成（R-22） |

### 6.2 食材字段与校验规则

| 字段 | 必填 | 校验规则 |
|---|---|---|
| 名称 | 是 | 非空；去除首尾空白与多余空格；长度 ≤ 80；拒绝换行等控制字符 |
| 类别 | 是 | 取自白名单：蔬菜 / 水果 / 肉类 / 海鲜 / 蛋奶 / 主食 / 调味 / 熟食 / 其他 |
| 数量 | 是 | 可解析为实数；必须为有限数且 > 0 |
| 单位 | 是 | 取自白名单：g、kg、ml、L、个、瓶、盒、包、袋、把、份 |
| 购买日期 | 否 | 可留空（留空 = 未知，与"今天购买"是两种不同状态，不得默认今天）；填写的日期必须合法且不得晚于今天 |
| 储存方式 | 是 | 取自白名单：冷藏 / 冷冻 / 常温 / 其他 |
| 保质期日期 | 否 | 合法日期；不得早于购买日期 |
| 保质期天数 | 否 | 整数且 > 0 |
| 过敏原声明 | 否 | 未声明时不得默认为"无过敏原"，必须记录为"未声明" |
| 备注 | 否 | 自由文本 |

同一名称再次入库时，**新增一条批次记录**，不得覆盖既有记录（R-15）。批次之间只要购买日期、保质期或储存方式不同，就必须分别保存（R-15、R-16）。

### 6.3 保质期规则（R-01 / R-02 / R-03 / R-04 / R-25 / R-26 / R-30）

设计前提：**用户自主录入明确有效期，系统不擅自把任何信息变成"正式有效期"**。

判定顺序是唯一的，不存在其他分支：

1. **用户填写了明确的有效期日期** → **原样保存**该日期（`expiry_source=user_date`），
   **不得**根据购买日期或参考期限覆盖或重新推算；也不要求购买日期已知。
2. **日期与保质期天数都提供且不一致** → 按 R-04：以**日期**作为正式记录，同时保留天数原值，
   并把提示文案改为"请确认哪个正确"；**该提示必须持久可见**（见下方展示约束）。
3. **用户只填写了保质期天数**（没有明确日期）→ 保留天数原值，**正式有效期日期保持为空**
   （`expiry_source=user_days_unresolved`）；系统**不得**把天数换算成正式有效期。
4. **用户没有填写任何期限信息** → 正式有效期日期保持为空（`expiry_source=unknown`）。

AI 估算（R-30，取代旧版"按天数换算成日期"的做法）：

5. 当**没有明确有效期日期**、且**用户填写了购买日期**时，系统可以给出针对该批次的 **AI 估算**：
   以食材类别与储存方式对应的经验区间为天数范围，加上该批次的购买日期，得到估算日期区间。
   - AI 估算**只用于展示**：绝不写入 `expiry_date`，也不参与新鲜度分级；
   - 必须明确标注"AI 估算"，并带"这是系统估算，不是你提供的有效期，也不是食品安全保证"；
   - 类别或储存方式缺失、为"其他"、或未收录该组合时，返回"未生成（未收录…）"，不得猜测；
   - V1 的 AI 估算由**本地经验规则**计算，不调用外部模型；接入模型后它依然是估算。
6. **没有购买日期时不生成任何 AI 估算日期**，也不得默认购买日期为今天（R-26）。

购买日期的处理（R-25）：

7. 购买日期由用户**主动填写**，**允许留空**；留空表示"未知"，与"今天购买"是两种不同状态。
8. 界面可以在用户确认后使用"今天"，但不得默认预选；记录中保留"是否采用了默认值"的标记，
   以便与用户确认过的日期区分。

展示约束（R-02、R-03、R-30）：

- 「正式有效期」只显示用户填写的日期；没有时显示"未知"。
- 「参考信息」显示**通用**经验区间（类别 + 储存方式），**不换算成日期**，且必须带上
  "参考信息，非食品安全保证"。
- 「AI 估算」显示针对该批次的估算日期区间与依据，例如"AI 估算：约 2026-10-14 ~ 2026-10-18
  （约 3–7 天，依据：购买日期 + 常见叶菜类 / 冷藏）。这是系统估算，不是你提供的有效期，也不是食品安全保证。"
  缺少购买日期时显示"AI 估算：未生成（缺少购买日期，不默认使用今天）。"
- **通用参考区间与 AI 估算必须分列展示**，不得把通用区间冒充为针对当前食材的 AI 估算。
- **新鲜度分级（过期 / 临期 / 新鲜）仅在 `expiry_source` 为 `user_date` 时给出**
  （历史数据的 `user_days` 同样可分级）；`user_days_unresolved` 与 `unknown` 一律为"未知"，
  参考区间与 AI 估算都不得把状态提升为"新鲜"或"安全"。
- 日期与天数的冲突提示必须**持久可见**（渲染在批次明细的"提示"列），不能只出现在保存成功的那一刻。
- 参考表只收录有限组合，未收录即未知；禁止为所有食材生成确定的到期日期。

参考数据的归属（R-03）：

- 参考期限数据属于日期领域逻辑（`core/dates.py`），必须同时记录参考期限与它的依据或来源；V1 只维护有限、可核实的参考表（当前为粗略经验区间，来源待补）。
- 配置文件不保存参考数据副本，只保存 `DUE_SOON_DAYS = 2` 这类固定业务常量与路径、密钥等运行参数。
- `DUE_SOON_DAYS = 2` 在 V1 作为固定业务常量使用，不提供用户配置功能。
- 参考区间与 AI 估算都是纯函数输出、**都不落库**，必须与用户填写的正式有效期在措辞与呈现上明确区分。

### 6.4 过敏原规则（R-05 / R-06 / R-07 / R-08 / R-14）

判定由 Python 代码完成，流程：食材与过敏原名称归一化（小写、去空白、去括号内容）→ 与用户过敏原及其内置别名表比对 → 输出三态之一。

| 状态 | 触发条件 | 产品处理 |
|---|---|---|
| `conflict` | 归一化后命中用户声明的过敏原或其别名 | **排除整道菜谱**，并说明命中了哪一项 |
| `unverifiable` | 食材过敏原声明状态为"未声明"；或命中复合调味料清单（如酱油、蚝油、沙茶酱等已知可能含大豆 / 小麦 / 麸质的复合品）；或菜谱引用了库存中不存在的食材 | **不得作为普通推荐**，该菜谱进入独立"待核实区域"，并显示警告"成分无法确认，可能含 X，请自行核实" |
| `none_known` | 未发现命中 | 作为普通推荐展示，但必须同时显示"未发现已知冲突（不代表安全）" |

展示约束：

- "待核实区域"是与普通推荐列表**分离的独立区块**，需要用户主动展开查看，且不使用与普通推荐相同的样式与措辞。
- 待核实区域必须有清晰可见的提示（标题、计数或警示文案之一，出现在折叠状态下即可看到）；展开后必须列出无法核实的**具体成分名称**与**风险原因**（例如"酱油可能含大豆，与你声明的大豆过敏相关"）。
- 任何位置都不得出现"安全""无过敏原""过敏友好"等表述（R-08）。
- 成分未声明的食材在明细中必须可见地标记为"成分未声明"（R-14）。
- 产品**不承诺**参考区间或过滤结果能覆盖真实配料；复合调味料的实际成分、AI 编造的食材名称均可能在能力之外，此局限由用户在界面上可见地知悉。
- 判定必须同时检查食材名称、食材上声明的过敏原信息、内置别名与已知复合调味料风险，不能只根据食材名称做判断（R-05、R-14）。
- **过敏原声明按批次独立保存与判定**：同一食材的不同批次各自的 `allergen_status` 与 `declared_allergens` 互不继承、互不覆盖（R-15、R-14）。只要菜谱用到的任一活动批次成分未声明，且用户已声明相关过敏原，该菜谱即进入待核实区域；不得用某一批次的声明代表同名食材的所有批次。
- 若用户**未声明任何过敏原**，则不存在待核实的约束对象：此时不对菜谱做待核实分流，菜谱作为普通推荐展示，食材仍标注"成分未声明"。不得因为"某食材未声明成分"就断定所有菜谱都与用户要求冲突。
- 无法可靠判断时，一律归入待核实（`unverifiable`），不得通过模糊猜测强行判定为无冲突（R-06、R-19）。

### 6.5 批次与库存闭环（R-15 / R-16 / R-23）

完整闭环：

首次初始化库存 → 购买食材并入库 → 查询库存与规划菜谱 → 用户选择菜谱 → 确认实际消耗 → 更新库存并记录事件。

各步骤的规则：

1. **首次初始化**：用户录入冰箱中已有的食材，建立初始库存。购买日期未知时必须显式选择"未知"（R-25）。
2. **购买入库**：每次购买都新增一条批次记录，即使食材名称与已有记录相同也不得覆盖（R-15）。
3. **查询与规划**：只读，不改变数量。
4. **用户选择菜谱**：基于最新库存重算（R-17），见 6.7 与 6.8。
5. **确认实际消耗**：用户确认后，在同一事务内更新库存、写入事件并更新规划状态（R-22）。

批次规则：

- 每个批次独立保存数量、购买日期、保质期信息与状态；批次之间不合并、不覆盖。
- 界面按食材名称汇总展示总量，同时保留展开查看各批次明细的能力。
- 汇总库存必须始终等于"同名且同单位"的活动批次数量之和，任何时刻不得出现不一致（可被测试断言）。
- 消耗时必须指定批次；用户未指定时，系统按下列**明确、可解释**的规则分配：
  1. 先消耗**有用户提供期限**的活动批次，按期限从早到晚（先到期先消耗）；
  2. 期限相同的，按购买日期从早到晚；购买日期未知的批次排在已知日期之后；
  3. 仍相同的，按批次记录创建顺序（id 升序）；
  4. **期限未知的批次一律排在已知期限批次之后**，不参与"先到期"排序，也不为其推断或伪造到期日期。
- 分配结果必须在界面上可见（哪个批次被消耗了多少），并可通过测试复现（R-16）。
- 菜谱规划确认消耗时同样按本节的分配规则把一道菜的食材需求分摊到多个批次，见 6.8（R-29）。
- 用户暂时取出食材（例如取出、暂放他处）**不改变库存**；只有确认实际消耗或丢弃后才减少。

### 6.6 库存规则与事件语义（R-09 / R-10 / R-12 / R-23 / R-24）

- 数量变更只发生在：初始入库、后续购买入库、数量编辑、消耗、丢弃、用户确认菜谱实际用量。
- 需要写入事件的操作：**初始入库、后续购买入库、数量编辑、消耗、丢弃、确认菜谱用量**，共六类；查询、规划、查看批次不写事件。
- 审计范围：**所有库存数量变化都必须有事件记录**；上述六类操作只要改变了数量就必须写事件，`qty_delta` 为 0 的操作不写事件。事件的 `item_id` 指向具体批次，因此多批次扣减会产生多条事件（R-12、R-29）。
- 事件数量语义统一为 `qty_delta = 变更后数量 − 变更前数量`：新增为正数，消耗与丢弃为负数，数量编辑记录差值（R-23）。
- 消耗/丢弃量必须大于 0 且不得超过剩余量；判定在数据层完成，不依赖界面拦截（R-24）。
- 数量不明确时应向用户追问，不得猜测或填入默认数量（R-24）。
- 任何入口（V1 为表单，V2 可能为对话）写入数量前都必须经过同样的 Python 校验与用户确认；AI 不得直接决定数据库中的最终数量（R-10）。
- 菜谱规划阶段**只写入草稿记录，不触碰库存**（R-09）。

### 6.7 食谱规划规则（R-11 / R-13 / R-17 / R-18 / R-19 / R-20 / R-21 / R-28）

**已实现的范围（阶段 5 + 阶段 6）**：上面的第 1 ~ 7 步全部实现——取库存 → 生成候选 → 展示 → 用户选份数 →
按最新库存算现有量/缺少量/补购建议 → 用户确认实际消耗 → 在同一事务内更新库存并写入事件；
结构校验（R-13、R-21 响应级）与过敏原三态分流（R-06 ~ R-08、R-19）同样已实现。
第 6 步由 `services/recipe_service.apply_plan()` 承担：菜谱计划用量与用户确认的实际消耗量是两个量（R-28），
只有用户确认的数量会被扣减，未确认或确认为 0 的食材保持原样。

**尚未实现**：份数调整（R-27）目前只接受生成时指定的份数，模型返回的份数与请求不一致时只做提示、不做按比例重算；
菜谱不持久化（每次生成的规划只存在于当前 Streamlit 会话，见 6.8）；候选之间不做缺口合并
（R-20 已满足：只展示每道菜自己的缺口）。

- 规划输入是当前有效库存的真实数据；库存为空时直接提示，不发起 AI 请求。
- 统一的推荐与选择流程：
  1. Python 获取当前真实库存；
  2. AI 生成多个候选菜谱及其食材需求；
  3. 系统展示候选菜谱与推荐理由；
  4. 用户选择想做的菜并确定目标份数；
  5. Python 依据**最新库存**计算现有量、需求量、缺少量与补购建议；
  6. 用户完成烹饪后确认实际消耗量；
  7. Python 校验并更新库存、写入事件。
- 第 4 步之后必须重新读取库存，不得沿用第 2 步生成时的旧数量（R-17）。
- AI 不负责计算权威的库存数量、缺少数量与补购数量；这些数字全部由 Python 计算（R-10）。
- 多份候选菜谱之间可能互相替代，因此**不得把候选菜谱的缺少量相加**；V1 只对用户选中的菜谱展示缺口与补购建议（R-20）。
- 食材不足是正常业务情况，不属于 AI 错误：菜谱需要 4 个土豆而库存有 2 个时，显示缺少 2 个并给出补购建议，而不是拒绝整道菜谱（R-18）。
- 份数调整（R-18、R-27）：用户可以调整目标份数并重新计算需求；也可以要求重新生成适合较小份量的菜谱。规则如下：
  1. 缩放比例 = 目标份数 ÷ 菜谱原始份数，**所有相关食材使用同一比例**，不得只改其中一种；
  2. 缩放后的需求量保留 **2 位小数**（四舍五入），由 Python 计算，AI 不得自行决定取整结果；
  3. 不可分割单位（个 / 瓶 / 盒 / 包 / 袋 / 把 / 份）的缩放结果若为非整数，界面另行提示"建议按 N 个准备"（N = 向上取整），但记录中的需求量仍保留 2 位小数，不写入取整值；
  4. 不做跨维度单位换算；
  5. 缩放结果必须通过 Python 校验（有限数、> 0、单位合法），非法值直接拒绝；
  6. 缩放只影响**菜谱需求量**的展示与缺口计算，**不得改写用户已确认的实际消耗量**（R-28）。
- 负数、非有限数、非法单位或不符合业务规则的数量不得进入库存计算（R-24）。
- 未匹配食材按 6.9 处理，不得视为 0、不得计入可靠的缺失量与补购汇总（R-19）。
- 单位不一致时不换算，仅提示"单位不一致，需人工确认"，不参与补购汇总。
- 缺失量计算仅对 `matched` 且数量已知的食材执行：缺失量 = 较大值(0, 需求数量 − 现有数量)。

### 6.8 确认消耗与库存一致性（R-09 / R-12 / R-17 / R-22 / R-24 / R-28 / R-29）

- 用户勾选实际用量并确认后，库存检查、库存更新、事件写入与规划状态更新在**同一个 SQLite 连接与事务**内完成；任一步失败则整体回滚，库存保持不变（R-22）。
- **菜谱需求量与实际消耗量是两个不同的量**（R-28）：需求量是 6.7 按份数换算出的理论值；实际消耗量由用户在确认环节输入，用于真正扣减库存。两者可以不同。
- 用户可以**只确认部分食材**的实际消耗；未确认的食材不做任何库存变动，并在界面上明确标注为"未确认"。已确认的食材按用户输入的数量扣减，Python 只校验（有限数、> 0、不超过该食材的可用量），**不得静默修改或按比例改写**用户确认的数量。
- 一种食材分布在多个批次时，Python 按 6.5 的分配规则计算**每个批次的扣减量**（R-29）：先用完靠前的批次再进入下一个批次，每个批次的扣减各自更新该批次库存、各自写入一条事件（`item_id` 指向该批次）。
- 若用户明确指定了批次，则只扣减指定批次，不做跨批次自动补足。
- 同一业务操作涉及的所有仓储操作必须共用同一个连接与事务，不得各自开事务（R-22）。
- 多批次扣减、多食材扣减、对应的事件写入与规划状态更新全部在**同一事务**内完成；任一批次扣减失败（例如受影响行数为 0）即整体回滚（R-22、R-29）。
- 已应用的规划不可重复应用：规划状态在事务内由"草稿"改为"已应用"，重复提交时条件更新影响行数为 0，操作被拒绝（R-22）。
- 用户选择菜谱时与确认消耗时都必须重新检查相关库存状态，不得仅依赖生成规划时的旧数量（R-17）。
- 若规划所需食材的可用数量已变化，则重新计算缺口；若用户确认的实际消耗超过最新库存，则**拒绝整个操作并回滚**，提示用户核实（R-24）。
- 一致性检查采用简单、可测试的方式，不引入版本号体系：在同一事务内先读取当前数量、再以"数量足够"为条件执行更新、并校验受影响行数；行数不符即视为库存已变化并回滚。
- 规划状态与库存的关系：规划本身不扣减库存（R-09）；只有确认消耗才写入数量变更与事件。

**实现说明（阶段 6）**：`apply_plan()` 在**外层事务**内重新读取最新库存与最新过敏原声明，再按用户确认的数量
逐食材、逐批次扣减（`inventory_service.consume(source="recipe_plan", plan_id=…)`）；任一食材或批次失败即整体回滚，
库存与事件都不变。防重复应用依赖 **Streamlit 会话状态**里记录的已应用 `plan_id`：
本版本**不新增持久化规划表**（数据库版本仍为 3），因此应用重启或跨会话后，同一份规划可以被再次确认扣减——
本版本不声称具备数据库级的幂等保障。`plan_id` 只在当前会话与库存事件表内可追溯。

### 6.9 未匹配食材与"未知"语义（R-19 / R-24）

- AI 提出的食材若无法匹配到库存记录，显示其名称并标记为"未匹配"。
- 未匹配**不得**解释为"用户家里没有这种食材"，**不得**把未知库存量伪装为 0，**不得**把未经确认的数量纳入可靠的缺失量或补购数量汇总。
- 数据层必须区分"未知"与数值 0：未知使用 NULL，0 表示确认过的零数量。任何汇总只累计数量已知的条目。
- **什么算"已知为零（0）"**：系统能依据有效库存记录与库存变更记录确认该食材当前没有剩余库存。典型情形是该食材曾经有批次，而这些批次已全部消耗或丢弃且没有新增批次。此时现有量为 0，**允许正常计算缺少量与补购建议**。
- **什么算"未知（NULL）"**：AI 提出的食材无法匹配到任何库存记录（从未有过该食材的记录），或记录状态不足以确认当前库存。此时现有量为 NULL，必须显示"库存情况未知，需你确认"，不得当作零，也不得纳入可靠的缺少量与补购数量汇总。
- 判定依据是"是否存在可确认该食材的库存记录"，而不是"当前是否存在活动批次"：批次全部耗尽属于**已知为零**，不得仅因为没有活动批次就升级为未知（R-19）。
- 若确实无法确认当前库存，保留 NULL，不得为了生成补购建议而猜测为 0（R-24）。
- 用户确认该食材的实际库存情况后，才依据已确认的信息重新计算缺口与补购建议。
- 单位不一致（`unit_mismatch`）同样不参与补购汇总，只做提示；它与"未匹配"是两种不同的状态，不得合并。

### 6.10 AI 输出校验分层（R-13 / R-21）

必须区分结构校验与业务校验：

| 层级 | 触发条件 | 处理 |
|---|---|---|
| 响应级（结构校验） | 整份响应无法解析为 JSON、或不符合严格 Schema（字段缺失、多余字段、类型错误） | **拒绝整份响应**，提示"AI 返回格式不合法"，不展示半成品 |
| 菜谱级（业务校验） | 通过 Schema 后，个别菜谱出现业务错误，例如数量 ≤ 0、非有限数、缺少推荐理由、菜谱内无任何有效食材 | **丢弃该菜谱，保留其他合法菜谱**，并提示被丢弃的数量与原因 |
| 条目级（业务处理，非错误） | 未匹配食材、数量不足、单位不一致、成分无法核实 | 按 6.7、6.8、6.9 的业务规则处理，**不得**因此判定整份 AI 响应失败 |

- 非法负数、非有限数量、非法字段类型等问题必须在相应校验层被拒绝，不得向下游传递。
- AI 调用失败（超时、网络错误、密钥无效）时显示清晰错误信息，且不得修改库存。
- 不得通过自动补默认值、猜测缺失数据或静默修补非法数据来绕过校验（R-13）。

## 7. 核心用户流程与异常场景

### 7.1 首次初始化与购买入库

填写名称、类别、数量、单位、购买日期、储存方式、保质期信息、过敏原声明 → 校验 → 保存为**一条新的批次记录**。

| 异常 | 处理 |
|---|---|
| 名称为空 / 仅空白 / 超长 / 含控制字符 | 拒绝并提示 |
| 数量为空、非数字、非有限数、≤ 0 | 拒绝 |
| 单位或类别或储存方式不在白名单 | 拒绝（界面提供选择而非自由输入） |
| 购买日期晚于今天 | 拒绝 |
| 首次录入已有食材但购买日期未知 | 必须显式选择"购买日期未知"，记为未知状态，不得默认为当天（R-25） |
| 未填购买日期（任何模式） | 允许留空，记为"未知"；不得默认当天（R-25） |
| 用户日期早于购买日期（仅当购买日期已知时校验） | 拒绝 |
| 用户天数 ≤ 0 | 拒绝 |
| 只填了保质期天数、没有明确日期 | 接受：保留天数、正式期限日期为空、分级为"未知"；有购买日期时另行展示"AI 估算"（R-26、R-30） |
| 用户日期与用户天数冲突 | 接受，按日期记录，提示冲突（R-04） |
| 未提供保质期信息 | 接受，按 6.3 处理 |
| 未声明过敏原 | 接受，状态标记为"未声明"（R-14） |
| 名称与已有批次相同 | 不覆盖，新增独立批次（R-15） |

### 7.2 消耗 / 丢弃（含批次分配）

用户选择食材（或某一条批次）并输入数量 → 确认 → 在同一事务内更新库存并写事件。

| 异常 | 处理 |
|---|---|
| 数量 > 可用库存 | 拒绝并提示可用量，不产生任何变更（R-24） |
| 数量 ≤ 0 或非数字 | 拒绝 |
| 记录不存在或状态非"在库" | 拒绝并提示刷新 |
| 未指定批次 | 按 6.5 的固定顺序分配，并在界面显示分配结果（R-16） |
| 指定批次但该批次数量不足 | 拒绝，提示该批次剩余量；不自动跨批次补足，除非用户选择"按规则自动分配" |
| 分配后汇总与批次不一致 | 视为实现缺陷；汇总必须始终等于批次之和（6.5） |

### 7.3 食谱规划与用户选择

流程与校验规则见 6.7、6.9、6.10。

| 异常 | 处理 |
|---|---|
| 库存为空 | 不发起请求，提示先录入食材 |
| AI 超时或网络错误 | 显示可读错误与重试入口，不改变任何状态 |
| 整份返回非 JSON / Schema 不符 | 拒绝整份响应（R-21） |
| 单道菜谱数量 ≤ 0、非有限数、缺推荐理由、无有效食材 | 丢弃该菜谱，保留其他合法菜谱并提示（R-21） |
| 引用用户已确认的过敏原 | 整道菜谱排除并说明命中了哪一项（R-05、R-06） |
| 用户已声明过敏原且成分无法核实 | 进入"待核实区域"，折叠状态下可见提示，展开后列出成分与风险原因（R-07） |
| 用户未声明任何过敏原 | 不做待核实分流，菜谱作为普通推荐，食材仍标注"成分未声明"（6.4） |
| 未发现已知冲突 | 正常展示，附"未发现已知冲突（不代表安全）"（R-08） |
| 编造库存中不存在的食材 | 标记"未匹配"，数量记为未知（NULL），不计入缺失与补购（R-19） |
| 食材曾有批次但已全部消耗或丢弃 | 按"已知为零"处理：现有量为 0，正常给出缺少量与补购建议（6.9） |
| 单位与库存不一致 | 只提示，不换算、不参与补购汇总 |
| 食材数量不足 | 正常展示现有量、需求量、缺少量与补购建议（R-18） |
| 用户调整份数 | 所有相关食材按**同一比例**换算，保留 2 位小数（四舍五入）；计件单位另给"建议按整数准备"提示；非法值拒绝（R-18、R-27） |

### 7.4 确认消耗

| 异常 | 处理 |
|---|---|
| 确认量 > 最新库存 | 拒绝整个操作并回滚，提示用户核实（R-22、R-24） |
| 期间库存已被修改 | 重新计算缺口；若仍满足则按最新库存执行，若不满足则拒绝并回滚（R-17） |
| 重复确认 | 被拒，提示该规划已应用（R-22） |
| 规划涉及的批次已被删除或状态已变更 | 条件更新影响行数为 0，整体回滚 |
| 用户只确认了部分食材 | 只对已确认的条目执行扣减；未确认条目保持原状并在界面标注为"未确认"（R-28） |
| 用户确认的数量少于菜谱需求量 | 按用户确认量扣减；未用到的量视为未消耗（R-28） |
| 用户确认的数量多于菜谱需求量 | 允许，但不得超过该食材的可用库存；超出可用库存则拒绝整个操作（R-24） |
| 一种食材分布在多个批次 | Python 按 6.5 的规则分摊到各批次，逐批次扣减库存并逐条写入事件（R-29） |
| 某批次扣减失败 | 整体回滚，其他食材与其他批次的扣减、事件一并撤销（R-22、R-29） |
| 用户未确认任何食材 | 不产生任何扣减与事件，规划保持草稿状态 |

### 7.5 库存变化后的重新计算

| 场景 | 处理 |
|---|---|
| 生成规划后库存增加 | 用户选择菜谱时按最新数量重算，缺口相应减少 |
| 生成规划后库存减少 | 重算后缺口增大；用户仍可继续，缺口按最新值展示 |
| 生成规划后批次被消耗或丢弃 | 该食材若曾匹配到库存记录、只是批次已全部消耗或丢弃，则可确认当前没有剩余 → 现有量为 **0**，正常计算缺口与补购；只有从未匹配到任何库存记录、系统无法确认时才保留为"未知"（NULL）（6.9、R-19） |
| 规划的菜谱已被应用 | 再次进入确认流程时被拒绝，需重新生成规划（R-22） |

## 10. 用户可见的文案约束

- 不得出现"安全""保证""一定不会过期"等绝对表述（R-02、R-03、R-08）。
- 参考区间必须与"非食品安全保证"同时出现。
- AI 估算必须标注为"AI 估算"，并与用户填写的有效期、通用参考区间分开呈现（R-30）。
- 日期与天数的冲突提示必须持久可见，不能只在保存成功后短暂出现。
- 待核实区域必须在折叠状态下就有可见提示，展开后给出无法核实的成分与风险原因，并提供"请自行核实"指引（R-07）。
- 未匹配食材必须表述为"库存情况未知，需你确认"，不得表述为"家里没有"或数量为 0（R-19）。
- 份额调整与缺口展示不得暗示"必需补购整份菜谱的全部食材"；补购建议只针对用户选中的菜谱（R-18、R-20）。
- 任何被拒绝的操作都必须给出可读原因，不得静默失败。

## 11. 已知局限（用户可见）

- 参考区间基于内置的有限参考表，覆盖范围有限，未收录即未知。
- AI 估算由本地经验区间 + 购买日期算出，可能偏宽或偏窄；它不使用用户填写的保质期天数，也不构成食品安全依据。
- 过敏原过滤只能处理已知名称与已知别名，无法判断复合调味料的真实配料，也无法核实 AI 编造的食材名称。
- 食材名称匹配采用归一化精确匹配，不做模糊猜测；匹配不到即标注需人工确认。
- 批次消耗分配是固定规则，不做用户自定义策略；期限未知的批次只能排在已知期限批次之后，无法给出"最该先吃"的判断。
- 汇总库存按"同名 + 同单位"计算；同名但单位不同的批次不合并汇总，也不会被自动换算。
- 份数缩放的 2 位小数与"建议按整数准备"仅为展示与参考，实际用多少由用户确认；系统不会把用户确认的数量改成取整后的值。
